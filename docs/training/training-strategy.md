# Artemis — Training Strategy

**Status:** Initial training plan; compute-dependent choices are intentionally open.

## 1. Objective

Train Artemis's foundation model from random initialization, then improve it through supervised and outcome-based post-training. Keep training reproducible, auditable, and reversible.

## 2. Data pipeline

```text
SOURCES
  -> ACQUISITION & PERMISSION RECORD
  -> FORMAT NORMALISATION
  -> QUALITY / LANGUAGE / TYPE CLASSIFICATION
  -> PRIVACY & POLICY FILTERS
  -> EXACT + NEAR-DUPLICATE DETECTION
  -> LICENCE / PROVENANCE VALIDATION
  -> BENCHMARK CONTAMINATION REVIEW
  -> MIXTURE & SPLIT GENERATION
  -> VERSIONED DATASET MANIFEST
  -> TRAINING
```

A rejected, excluded, or quarantined record should have a recorded reason. Data transformations must be versioned so a training run can be reproduced.

## 3. Data families

Potential families, pending permission and quality review:

- General prose and reference material.
- Technical documentation and educational material.
- Source code and repository-level examples with compatible licences.
- Mathematics and scientific problem sets.
- Tool-use and structured interaction examples.
- Multilingual material, including Bengali and English.
- Human-authored instruction and preference data.
- Synthetic tasks generated by deterministic programs and verified tools.

Do not assume that public availability means unrestricted training permission. Record terms and legal basis for each source. Do not scrape private content or collect secrets.

## 4. Code-data quality

Where feasible, repository-level samples should include:
- Repository and commit identity.
- Licence.
- File paths and language.
- Build/test instructions.
- Dependency and environment metadata.
- Test outcomes when executed.
- Whether examples are synthetic, transformed, or original.
- Any known limitations.

Prefer examples with meaningful context and verifiable outcomes over isolated snippets with no provenance.

## 5. Synthetic data and verification

Synthetic examples can expand task coverage, especially for:
- Algorithm implementation.
- Unit-test generation.
- Bug injection and repair.
- Type and API constraints.
- Mathematics with exact answers.
- Tool-use simulations.
- Repository navigation tasks.

Use compilers, interpreters, tests, reference solvers, theorem checkers, and deterministic validators when available. Store generation prompts, seeds, validator versions, and pass/fail outcomes. Synthetic data must be audited for diversity and repetitive artefacts.

## 6. Dataset splits and contamination control

Maintain train, validation, and held-out evaluation sets. Evaluation tasks should not silently migrate into training. Track benchmark versions and known overlaps. Use temporal or repository-level separation where it improves independence.

## 7. Training phases

### Phase A — technical validation
- Tokenizer correctness and corpus statistics.
- Data loader throughput and sampling.
- Tiny random-init training run.
- Loss monitoring and gradient sanity checks.
- Checkpoint save, resume, and inference.
- Reproducibility across repeated runs.

### Phase B — baseline pretraining
Train a small decoder-only model from random initialization. The goal is to validate the recipe and establish capability/compute baselines, not to claim frontier performance.

### Phase C — foundation pretraining
Scale only after Phase B is stable. Preserve data mixture manifests and training logs.

### Phase D — supervised post-training
Train instruction following, conversation quality, code tasks, structured responses, and tool-call formats using curated examples.

### Phase E — outcome-focused optimisation
Use verifiable rewards where available: tests pass, builds succeed, exact answers match, tool arguments validate, and tasks meet acceptance criteria. Use human preferences and expert review for qualities without reliable automatic metrics.

### Phase F — continuous improvement
Collect candidate corrections and task trajectories. Curate them, deduplicate, validate, and add them to future training/evaluation cycles. Do not update production weights directly from every live conversation.

## 8. Interaction feedback loop

```text
INTERACTION
 -> CONSENTED / POLICY-COMPLIANT CAPTURE
 -> FAILURE OR SUCCESS DIAGNOSIS
 -> VERIFIED CORRECTION OR OUTCOME
 -> CURATED TRAINING EXAMPLE
 -> CANDIDATE TRAINING RUN
 -> REGRESSION + HELD-OUT EVALUATION
 -> APPROVAL / REJECTION
 -> VERSIONED CHECKPOINT
```

Memory updates and model-weight updates are different mechanisms. A verified fact may be written to a scoped memory store without changing model weights. Weight updates require a training job and release gate.

## 9. Reproducibility manifest

Every run must record:
- Run ID and timestamp.
- Git commit and environment.
- Model config and initialization seed.
- Tokenizer ID and hash.
- Dataset manifest IDs and hashes.
- Sampling weights and data order/seed controls.
- Optimiser, scheduler, precision, and batch configuration.
- Hardware topology and software versions.
- Checkpoint IDs and resume lineage.
- Metrics and evaluation report.

## 10. Compute policy

Do not set a final parameter count, token budget, context length, or training duration until workstation discovery and baseline runs. Keep large datasets and checkpoints outside Git. Use artifact storage with versioning, access control, integrity hashes, and backups.
