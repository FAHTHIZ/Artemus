Artemus is a research project about training a language model from random initialization.
A language model learns statistical structure by predicting the next token in a sequence.
The first implementation is intentionally small. It exists to test data loading, optimisation,
causal attention, checkpointing, and evaluation before any expensive scaling experiment begins.

Good software engineering requires understanding a program before changing it.
A careful engineer reads the project structure, identifies the entry points, studies the tests,
and writes down the expected behaviour. A patch is not complete merely because it looks correct.
The program should be run, its tests should be executed, and the final change should be reviewed.

A useful debugging process starts with an observable failure.
First reproduce the failure. Then reduce it to the smallest useful example.
Inspect the error message and the relevant code path. Form a hypothesis and test it.
Change one thing at a time when practical. Run the focused test again, then run regression tests.
Record what was tested and what could not be verified.

A small experimental model is not a substitute for a large model.
It helps identify training-pipeline mistakes before expensive experiments begin.

A test suite is a collection of executable expectations.
A passing test gives evidence about the behaviour it covers; it does not prove that every possible behaviour is correct.
An honest engineering report distinguishes observed results, assumptions, and unresolved questions.

The model should not treat stored parameters, active context, and external documents as the same kind of memory.
Parameters encode learned patterns. Context contains information currently available to the model.
External retrieval systems make selected documents available when a task requires them.
A reliable agent retrieves relevant information, uses tools under explicit permissions, and verifies results.

A training experiment should record its configuration, dataset manifest, tokenizer, random seed,
hardware, software versions, checkpoint lineage, and evaluation results.
Reproducibility makes it possible to compare experiments and identify real improvements.
A larger parameter count is not itself evidence of better capability.

In Python, a function should have a clear purpose and predictable inputs and outputs.
Tests should cover expected cases, edge cases, and invalid input.
When a function changes, tests should detect accidental changes in behaviour.
Readable code, good names, and small modules help people understand and maintain a system.

Artemus will grow through experiments. Each experiment should answer a question, produce evidence,
and preserve enough information for another person to reproduce the result.
